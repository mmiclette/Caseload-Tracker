# Hosting the prototype

A public, always-current demo of the registry: one container, one process,
no database service, and data that is always the same number of days away
from whatever today is when a visitor opens it.

Everything here is **additive**. Nothing under `app/` or `frontend/src/`
changed to make hosting work. Delete this directory, `Dockerfile` and
`render.yaml` and the registry is exactly what it was.

---

## Deploying to Render

1. Push this repository to GitHub.
2. In Render: **New + → Blueprint**, point it at the repository. It reads
   `render.yaml` and creates the service.
3. Wait for the first build (the frontend build plus the Python install —
   several minutes, mostly dependency installation).

That's it. `SECRET_KEY` is generated by Render on first deploy; everything
else is in `render.yaml`.

To deploy by hand instead of via blueprint: a Docker web service on this
repo, health check path `/healthz`, with `SECRET_KEY` set to any random
string and `DATABASE_URL` set to `sqlite:////data/cocm_demo.db`.

### Running the image locally

```bash
docker build -t cocm-demo .
docker run --rm -p 8000:8000 -e SECRET_KEY=local-dev cocm-demo
```

Or without Docker, from a checkout with `frontend/dist` already built:

```bash
DATABASE_URL=sqlite:///./cocm_demo.db SECRET_KEY=local bash deploy/entrypoint.sh
```

## How the data stays current

This is the part worth understanding, because it's the whole point.

`scripts/seed_demo.py` already dates everything **relative to the day it
runs** — `days_ago(16)`, `months_ago(14, 8)` — rather than to fixed
calendar dates. A patient isn't "enrolled 2026-10-06", she's "enrolled 16
days ago". That gives exactly the property asked for: scores are days old
rather than stale, reminders form a realistic slightly-overdue ladder, and
Quality Metrics has activity in all twelve months.

But that property only holds *on the day the seed ran*. A database seeded
in March and visited in October shows a caseload where every score carries
a staleness asterisk and every reminder is months overdue.

So the deployment records the date it last seeded, in a one-row
`demo_state` table, and **re-seeds whenever that date is no longer today**.
A visitor always lands on a caseload that looks like it was worked
yesterday, however long the service has been running.

That check happens in two places:

- **At boot**, in `entrypoint.sh` — covers restarts and redeploys, which on
  a free Render instance means roughly every cold start.
- **When someone loads the page**, in `demo_app.py`'s SPA route — covers a
  long-running instance crossing midnight. It is deliberately on the page
  load rather than on API requests, so a refresh never happens underneath
  an in-flight session's API traffic. Re-seeding takes about two seconds.
  Set `DEMO_REANCHOR_ON_LOAD=0` to freeze the data at whatever the last
  boot produced.

A signed-in user can also force it: `POST /api/demo/reset` puts the
scenario back to its known starting state after someone has been clicking
around.

### `demo_state` is not an Alembic migration, on purpose

It's deployment bookkeeping, not registry schema. The registry's schema has
to run unmodified against Postgres and Snowflake and is versioned by
Alembic; shipping a demo-only table through that chain would put it in
every environment that has no use for it. It's created directly by
`demo_data.py` instead, and lives outside `Base.metadata` so the wipe can't
delete the row recording that the wipe happened.

---

## Two things to know about this setup

**The schema comes from the models, not the migration chain.** On SQLite,
`alembic upgrade head` cannot run at all: migration `a3613a105946` issues
`ALTER COLUMN ... DROP DEFAULT`, which SQLite has no syntax for. That's not
a defect in the migrations — they're written for the two databases the
registry actually targets, and SQLite is neither. `deploy/demo_data.py`
uses `Base.metadata.create_all` instead, which is sound here specifically
because a demo database has no history to migrate: it's built from empty
every boot, so all that matters is arriving at the schema the models
describe. Building a schema straight from the models is also what
`tests/conftest.py` does (against Postgres), so it's an established route
in this codebase rather than something invented for the deploy.

That the models produce a *working SQLite* schema is evidenced directly:
the full demo seed runs green on it, and every report endpoint was queried
against the result.

The tradeoff, stated rather than buried: **the hosted demo exercises the
models but not the migration chain.** A migration that drifted from the
models wouldn't be caught here. Postgres remains where that gets verified,
via the upgrade/downgrade round-trip and from-scratch chain replay.

`ensure_schema` is dialect-aware, so pointing `DATABASE_URL` at a Postgres
instance instead runs the real migrations.

**The database is ephemeral.** Render's free tier has no persistent disk,
so the SQLite file lives on container disk and disappears on restart. For a
demo this is arguably the right behaviour rather than a limitation: a
restart returns the scenario to its known starting state, and the entrypoint
seeds an empty database automatically. Anything a visitor enters is theirs
until the next restart. To make it persistent, attach a Render disk mounted
at `/data` on a paid plan — no code change needed.

## Files

| File | What it does |
|---|---|
| `deploy/demo_app.py` | Outer app. Mounts the API at `/api`, serves the SPA with an index.html fallback so client-side routes survive a refresh, adds `/api/demo/{status,reset}`. |
| `deploy/demo_data.py` | Schema creation, the wipe, the re-seed, and the `demo_state` freshness marker. |
| `deploy/entrypoint.sh` | Boot: prepare database, re-anchor if stale, serve. |
| `Dockerfile` | Node stage builds the SPA; Python stage serves both. |
| `render.yaml` | Render blueprint. |

### Why mounting at `/api` means no frontend changes

In development, Vite proxies `/api/*` to the API. The frontend's client
therefore already calls `/api/...` everywhere. Mounting the existing app at
that same prefix in production means the client's URLs are correct with no
build-time base URL, no environment variable, and no CORS configuration —
the API and the SPA are the same origin.
