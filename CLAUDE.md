# CoCM Registry — Project Context

## What This Is

A Collaborative Care Model (CoCM) registry for Behavioral Health Care Managers (BHCMs) and Psychiatric Consultants. The registry tracks a caseload of patients through episodes of care, supports Systematic Caseload Review, and generates population-level and program-level reporting. The functional requirements follow the AIMS Center's Collaborative Care Registry Design Considerations guide.

## Tech Stack

- Backend: Python 3.12, FastAPI
- Data access: SQLAlchemy 2.0, repository pattern (no raw SQL scattered through route handlers)
- Local and test database: PostgreSQL, run via docker-compose
- Production database: Snowflake, connected through the snowflake-sqlalchemy dialect
- Frontend: React 18, TypeScript, Vite, standard SPA (no Next.js, this is an internal authenticated tool, not a public site)
- Target hosting: AWS, ECS Fargate for the API, S3/CloudFront or Amplify for the frontend

## Critical Portability Rule

Every schema definition and every query must run unmodified against both PostgreSQL and Snowflake. Postgres is the dev and test database. Snowflake is production. Do not write anything that only works on one of them. Specifically:

- Do not use SERIAL or BIGSERIAL primary keys. Use SQLAlchemy's Identity() construct instead, since both databases support IDENTITY columns but SERIAL is Postgres-only.
- Do not use JSONB. Use SQLAlchemy's generic JSON type, or store structured data as validated TEXT if the JSON type causes friction.
- Do not use Postgres-native upsert syntax such as ON CONFLICT. Handle upserts through the repository layer with an explicit select-then-insert-or-update pattern, or SQLAlchemy's merge().
- Do not rely on case-sensitive unquoted identifiers. Use lowercase snake_case for every table and column name, since Snowflake uppercases unquoted identifiers by default and Postgres lowercases them, and mismatched casing breaks portability silently.
- Do not use Postgres-only functions such as ILIKE. Use LOWER(x) LIKE LOWER(y) instead.
- Store every timestamp as timezone-aware UTC in both environments.
- Do not build anything around Snowflake Hybrid Tables or other Snowflake-only features. The schema needs to run on plain Postgres for local development.

## Data Model

Build these entities first. Field lists are a starting point, not a ceiling. This section was revised after screen-by-screen review of the AIMS Caseload Tracker (the CTMS we're modernizing) — see the CTMS Walkthrough Reference section below for the source material.

**Patient** — patient_id, mrn, name, payer, program_eligibility fields, date_of_birth, race_ethnicity, consent_date, enrollment_date, deactivation_date. Phase 1 kept a single clinic_id column here; Phase 2 removed it in favor of the Clinic Assignment table below, since a patient can belong to more than one clinic over time. race_ethnicity is optional and org-configurable — a multi-select over American Indian or Alaska Native, Asian, Black or African American, Hispanic or Latino, Middle Eastern or North African, Native Hawaiian or Pacific Islander, White, and Patient declined. Age is always computed from date_of_birth for display — never store it. Per AIMS guidance, patients enter the registry after they consent to treatment and are removed when they complete an episode of care, so enrollment and deactivation need explicit dates rather than implicit status.

Flags live on Patient, not Episode — the caseload list shows one Flags column per patient regardless of episode. There are three: a yellow flag (needs_psychiatric_review) that a Care Manager sets when requesting Systematic Caseload Review (via Contact.discuss_with_psychiatric_consultant, see Contact below) and that clears automatically once a Psychiatric Consultant records that review (via Consultation, see below); a red flag (safety_risk) for patient safety concerns; and a blue flag (custom_flag_active, custom_flag_label) with an org-configurable label for whatever else a program needs to track.

**Episode of Care** — episode_id, patient_id, start_date, primary_diagnosis, secondary_diagnosis, baseline_measure_type, baseline_score, baseline_date, end_date, end_reason. primary_diagnosis and secondary_diagnosis (Phase 7, both nullable ConditionType: depression, anxiety, ptsd, adhd, substance_use) are deliberately two columns, not a diagnosis join table — "primary and secondary" is exactly two slots, which is what keeps the caseload metric unambiguous. The primary diagnosis pins which measure the patient's response/remission reporting tracks, via CONDITION_MEASURES in app/services/scoring.py (depression → PHQ-9/SMFQ, anxiety → GAD-7/SCARED, ptsd → PCL-5, adhd → Vanderbilt, substance_use → nothing until AUDIT-C/DAST-10 exist); the secondary gets a dashboard trend graph but stays out of the headline rates. Episodes recorded before Phase 7 fall back to the condition their baseline measure implies (MEASURE_TO_CONDITION) — no backfill. A secondary requires a primary and must differ from it (EpisodeService validates both create and update). Soft baseline consistency: when a primary_diagnosis is set and the established baseline's measure is NOT one of its mapped candidates but an incoming score's measure IS, recompute_baseline re-anchors the index baseline onto the primary-mapped measure (if primary is anxiety, the baseline should be GAD-7 even when a PHQ-9 was recorded first); within the same condition's candidates, first-established still wins. end_reason is a deactivation reason, not a clinical outcome — the CTMS's own Completed Episode Statistics report uses: achieved_goals, not_engaged, patient_choice, patient_no_longer_available, patient_died, patient_died_by_suicide, other. Remission, response, and improvement are computed outcomes (see Symptom Score below) worked out at report time by comparing baseline and most-recent scores — they are never stored as an end_reason. The first validated score in the episode is the baseline. If a patient returns to treatment after a gap of six months or more, start a new episode with a new baseline rather than continuing the old one.

**Treatment Status** — Enum with three values: active_treatment, relapse_prevention_plan, deactivated. Track status_changed_date on every transition, since episode length reporting depends on it. Two transitions are automatic side effects rather than a second explicit call, per the CTMS's own behavior: recording an RPP Contact (see Contact below) transitions status to relapse_prevention_plan, and closing an episode (setting end_date) transitions status to deactivated. Both cascades are idempotent — recording a second RPP contact, or closing an already-closed episode, doesn't add a duplicate history row. These live in EpisodeService (update_episode) and ContactService (record_contact) respectively, never left for the frontend to trigger separately.

**Symptom Score** — score_id, patient_id, episode_id, contact_id, measure_type, score_value, score_date, recorded_by. Built in Phase 2: a score now always belongs to a real Contact (see Contact below), which is where contact_type, contact_date, and the provider live — Phase 1's interim contact_type column on Symptom Score is gone. patient_id and episode_id stay directly on this table (denormalized from Contact) since caseload and episode reporting query scores far more often than they need to join through Contact. Confirmed full measure_type list: PHQ9 and GAD7 for adults, PCL5 for PTSD, and three pediatric scales — SCARED (pediatric anxiety), SMFQ (pediatric depression), and Vanderbilt (pediatric ADHD). Remission for PHQ-9 is a score under 5. Remission for GAD-7 is also a score under 5 (confirmed by Matt 2026-08-07 — remission is not PHQ-9-only). Response is a 50 percent improvement from the episode's baseline score. Anxiety improvement/response on GAD-7 is a 5-point improvement from baseline. **Open question, needs AIMS clinical sign-off before any report leans on it**: the CTMS reports "PTSD Improvement" (PCL-5), "Pediatric Anxiety Improvement" (SCARED), "Pediatric Depression Response" (SMFQ), and "Pediatric ADHD Improvement" (Vanderbilt) as named metrics, but no walkthrough source has stated the numeric thresholds for these four yet. Don't invent them — the scoring service returns is_remission=False, is_response=False for any measure type without a defined rule, which is the correct conservative default until AIMS confirms real numbers. Build all of this as computed properties or a service function, not hardcoded thresholds duplicated across the codebase.

**Provider** (Phase 2 — built) — provider_id, name, role (care_manager, primary_care_provider, psychiatric_consultant, clinic_supervisor, data_analyst — matching the CTMS's account types), phone, email. Built ahead of real authentication, per the Phase 2 decision to avoid a later migration converting free-text recorded_by/changed_by columns into foreign keys right when reporting (caseload filtered by provider, "cover for a colleague's caseload") starts needing a real Provider to filter by. Contact.provider_id, CareTeamAssignment.provider_id, and Consultation.provider_id are all provider_id foreign keys now. TreatmentStatus.changed_by and SymptomScore.recorded_by remain free-text strings — nothing in the CTMS walkthrough required routing those through Provider yet, and they can move to provider_id later without a schema fight since they're plain nullable strings today, not something else depending on their shape.

**Contact** (Phase 2 — built) — contact_id, patient_id, episode_id (nullable — a contact_attempt need not reference an episode), provider_id, contact_type (initial_assessment, follow_up, relapse_prevention_plan, contact_attempt, care_team_collaboration — the last added Phase 9: about-the-patient work without the patient present; billable minutes but never scores, not a session/engagement, doesn't reset the attempt counter or reminder clock), contact_date, location, duration_minutes, discuss_with_psychiatric_consultant (boolean — this is what lights the yellow flag), notes_for_consultant, notes (Phase 8 — the encounter note itself: what happened during the visit, distinct from notes_for_consultant which is the message that travels with the yellow flag), attempt_number (nullable — only meaningful for contact_attempt rows, computed at write time), plus five Relapse Prevention Plan fields (Phase 10): other_treatments, personal_warning_signs, stress_reduction_plan, additional_comments, and medications_confirmation (a MedicationConfirmation enum — confirmed_with_patient / confirmed_in_medical_record / deferred, the CTMS's three exact checkboxes above its Current Medications table; unlike ContactLocation this vocabulary IS confirmed). The CTMS records an RPP as a contact — same date, same session footer, same save — so the plan lives on Contact rather than a separate entity, and an episode can hold several RPP contacts each carrying that session's version of the plan. ContactService rejects these five fields on any non-RPP contact type, naming the offenders. A "contact attempt" is outreach that didn't result in a completed session — the Reminders page tracks these separately with an attempt counter ("attempt #1", "attempt #2") that resets to 1 after any non-attempt contact. Recording a relapse_prevention_plan Contact carries forward the same Treatment Status cascade Phase 1 built for RPP Symptom Scores — see Treatment Status above — and likewise for whatever action closes out an episode (deactivation). All of this — baseline recompute, the RPP cascade, the flag cascade, attempt-number sequencing, and validation (a contact_attempt can't carry scores; scores require an episode_id) — lives in ContactService.record_contact, the single entry point for recording a visit or outreach attempt with everything collected during it in one call, matching the CTMS's own contact-recording form.

**Care Team Assignment** (Phase 2 — built) — care_team_assignment_id, patient_id, provider_id, role (care_manager, primary_care_provider, psychiatric_consultant — narrower than Provider's own role list, since clinic supervisors and data analysts never appear on a patient's care team), service_begin_date, service_end_date. The Clinical Dashboard's "Current Providers" table shows exactly this shape ("current" = service_end_date is null). A patient can have more than one provider per role over time and more than one current provider at once (a Care Manager and a Psychiatric Consultant simultaneously), so this is its own table, not columns on Patient.

**Clinic Assignment** (Phase 2 — built) — clinic_assignment_id, patient_id, clinic_id (a plain string identifier, not a foreign key to a separate Clinic entity — nothing in the data model calls for clinic name/address, only an identifier to group and filter by), is_primary, service_begin_date, service_end_date. Replaces Phase 1's single Patient.clinic_id column — the CTMS lets a patient belong to more than one clinic over time with a "primary" flag and service_begin/end dates (the Clinical Dashboard's "Current Clinics" table), which a single string column couldn't represent. PatientRepository.list_by_clinic now joins through this table and only considers current assignments.

**Consultation** (Phase 2 — built) — consultation_id, patient_id, provider_id (the psychiatric consultant, nullable), consultation_date, duration_minutes (Phase 9 — consultant time is billable CoCM time; counted by Minutes This Month and Monthly Time Tracker), recommendations_forwarded (boolean), flagged_for_next_review (boolean), flag_reason, notes (Phase 8 — the consultation note: the Psychiatric Consultant's findings and recommendations from the review; recommendations_forwarded tracks whether they reached the PCP). Recording a Consultation is what clears the yellow needs_psychiatric_review flag on Patient — ConsultationService.record_consultation always sets the flag to whatever flagged_for_next_review is on this consultation, so a consultation that itself flags a future review immediately re-sets the flag rather than leaving it cleared ("we reviewed this today" and "review this again next time" are different things).

**Reminder** (Phase 3 — built) — reminder_id, patient_id, episode_id (nullable), reminder_type (appointment, referral_followup), due_date, status, notes. Confirmed cadence, all three numbers living in exactly one place (ReminderService's module-level constants, per "don't hardcode... in more than one place" below): a reminder fires within 7 days of enrollment for a new episode, every 2 weeks during active_treatment, and every 4 weeks during relapse_prevention_plan once at least one real contact has happened. ReminderService.recompute_appointment_reminder upserts a single current pending appointment Reminder per patient — called after episode creation, after every recorded Contact, and after an episode closes (which dismisses it) — rather than leaving a pile of stale ones; a contact_attempt does not reset this clock, only a completed Contact does. status (pending, completed, dismissed) is a reasonable-not-confirmed placeholder vocabulary, same discipline as ContactLocation — the walkthrough never showed the Reminders page's own status/dismiss controls in enough detail to confirm exact wording.

The Reminders page also tracks contact attempts separately from completed contacts, with an attempt number (see Contact above), for patients a Care Manager hasn't been able to reach.

**Referral** (Phase 4 — built) — referral_id, patient_id, referred_by_provider_id (nullable), referred_to (a plain string, same "identifier, not a foreign key to a real entity" treatment as ClinicAssignment.clinic_id — nothing calls for a Referral Destination entity), referral_date, reason. Closes the gap the Phase 3 Reminder section used to flag: ReferralService.record_referral creates the Referral and its linked referral_followup Reminder (via Reminder.referral_id) in one call, so POST /referrals is now the only way a referral gets recorded — the old workaround of posting a bare referral_date straight to /reminders is gone, and that route no longer accepts one.

**Medication** (Phase 5 — built) — medication_id, patient_id, medication_key (nullable), medication_name, dose, frequency, is_current, stop_reason (nullable), recorded_by. The confirmed field spec is exactly: name, dose, frequency, current-or-past, and — if past — why it was stopped; no start/end dates were asked for. medication_key links to the vendored bh-cds medication catalog (app/vendor/medication_registry.py, copied byte-identical from bh-cds's Manage_Additions/backend/cds_core/medication_registry.py — see app/vendor/__init__.py for the re-sync rules) which backs the search-as-you-type med picker via GET /medications/catalog?q= (display names, class, real FDA dose steps, with display_doses for combination products like buprenorphine/naloxone). The key is nullable because patients take non-BH medications (e.g. metformin) recorded as free text. dose is a string, not a number ("8mg/2mg"); frequency and stop_reason are free text — no confirmed vocabulary exists for either, same "flag it, don't invent it" discipline as ContactLocation. MedicationService enforces: a catalog key must be real and its display name always comes from the catalog; stop_reason is rejected on a current medication (though it's not *required* on a past one — unknown history is real data); restarting a medication clears its stop_reason; identity fields never change on update — a different medication is a new row. Note the AIMS guide lists medications, but the CTMS walkthrough never showed a medications screen — this entity follows the design-considerations guide beyond confirmed CTMS parity, a deliberate product extension.

**Profile Entry** (Phase 6 — built) — profile_entry_id, patient_id, section (ProfileSection enum), sub_field, value, context, recorded_date, recorded_by. The generic entity behind the patient profile's free-form sections, from the 2026-08 patient-profile design's "Bucket B": Behavioral Health, Medical Profile, Safety & Risk, Substance Use, Social & Environmental, plus allergies/intolerances under Current Medications (the *only* sub-field that section gets here — medications themselves are Medication rows, never free text). The interaction model is click-a-sub-field, add-a-value: each entry carries a clinical recorded_date (defaults to today) and optional context. The table is **append-only** — no update or delete routes exist, on purpose; a changed circumstance or a typo is a new entry that supersedes the old at display time (ProfileEntryRepository orders newest-first per sub-field, ties broken by insert order). sub_field is a plain string: the per-section defaults live in ProfileEntryService.SECTION_SUB_FIELD_SUGGESTIONS (served by GET /profile-entries/sections for the picker) as suggestions, not validation — expected to become org-configurable once an Organization entity exists. Safety & Risk entries document risk factors, but Patient.safety_risk (the red flag) remains the single alerting signal — an entry never sets or clears it. Buckets A and C from the same design are not built yet: A is composition of existing entities plus AUDIT-C/DAST-10 MeasureTypes (unscored) and a therapist CareTeamRole; C is Vitals & Monitoring and Laboratory Results as new ProfileSection values with numeric_value/unit columns added to this same table.

**Audit Log** (Phase 13 — built) — audit_log_id, occurred_at (indexed), actor_provider_id (FK, nullable) + actor_label, action (AuditAction enum), entity_type, entity_id, patient_id (FK, indexed), field, old_value, new_value, context. Satisfies the PHI rule below: every write to patient status, a flag, or a score records who/what/when. AuditAction covers status_changed, flag_set, flag_cleared, score_recorded, episode_opened, episode_closed, patient_deactivated, patient_updated.

Design points worth not re-litigating: **actor_label duplicates the provider's name on purpose** — an audit trail whose account of the past changes when a Provider is renamed is not an audit trail, so the FK gives joins and the label gives history. **old_value/new_value are plain strings** (rendered by `_render` in app/services/audit.py) because the audited fields span booleans, dates, ints and enums; one readable text form keeps the table portable (no JSONB) and legible to a human reviewer. **patient_id is denormalized onto every row** so one patient's trail is a single indexed query instead of a union across entity types. **The table is append-only**: there is no POST/PATCH/DELETE on /audit-log, only GET — writes happen exclusively as a side effect inside AuditService.

Actor plumbing: routes bind `actor: Provider = Depends(get_current_provider)` and pass it into the service. FastAPI caches that dependency per request, so binding it alongside the existing router-level check costs no extra lookup. `actor` is optional because scripts (create_admin_provider.py, the seeds) write through the service layer with no authenticated provider, and an entry recording what/when with an unknown actor beats no entry. tests/test_audit_log.py::test_routes_record_the_authenticated_actor drives the real HTTP write routes and asserts **zero** anonymous entries, so a route that forgets to pass the actor fails loudly rather than silently logging anonymously.

**Known limitation, stated rather than hidden:** each audit entry commits in its own transaction, because BaseRepository.create commits and the service layer already commits per repository call. A change and its audit entry are therefore not atomic. Making them atomic needs a session-scoped unit of work across the whole service layer — worth doing, much larger than this table, and doing it badly would be worse. Documented in app/services/audit.py's module docstring.

**Multi-tenancy (not yet built, decisions recorded)** — this registry is single-tenant today: no Organization entity, no org_id/tenant_id column anywhere in the schema. Two things are decided for when that changes: a future tenant will be an Organization corresponding to one NeuroFlow customer org (a behavioral health practice licensing the registry, potentially with many clinics/providers/patients of its own) — not the existing Clinic Assignment concept, which stays a sub-org grouping under whichever Organization a patient belongs to. Until Organization exists, any org-level toggle (see Monthly Time Tracker below) is a plain global settings flag in app/core/config.py, not a database row — there's nowhere per-org for a database row to live yet, and standing up a table for a single-tenant deployment just to hold one flag was explicitly decided against in favor of the simpler config-based approach.

## Reporting Requirements

These come later in the build, listed here so the data model supports them from the start. Report shapes below are transcribed from the CTMS walkthrough, not invented — see the Walkthrough Reference section for context.

- Reminders (BHCM landing page on login) — **built**: GET /reminders with no patient_id returns every pending Reminder, due-date order, matching the landing page. This is a simpler shape than the original "days-until/overdue for Initial Assessment and Follow-Up, and Last Contact Attempt with an attempt number" description — it lists Reminder rows directly rather than deriving separate per-measure countdown columns, since ReminderService already collapses those into a single due_date per patient. Revisit this if the frontend screenshots (see Frontend Design and Branding) show more columns than that.
- Caseload-level report ("Active Patients") — **built**: GET /reports/active-patients, filterable by payer, clinic_id, and provider_id (so one Care Manager can cover another's caseload during leave). Returns one row per patient with an open episode and a non-deactivated Treatment Status: Flags, Patient ID, MRN, Name, Age, Status, PHQ-9/GAD-7/PCL-5 (first/last score in the current episode), Initial Assessment date, Follow-Up date (most recent), Psychiatric Consultation (an ISO date, or the literal string "CONSIDER" while needs_psychiatric_review is set and not yet cleared by a Consultation), Relapse Prevention Plan date (most recent), # Sessions (completed contacts in the episode, excluding contact_attempt), Weeks since Initial Assessment, and Minutes This Month. See app/services/reporting.py's module docstring for why this is a straightforward per-patient loop rather than one aggregate SQL query. Deactivate remains a UI action against the existing PATCH /episodes/{id} endpoint, not a report column. Phase 5 added the AIMS guide's "whether psychotropic medications are prescribed" column (psychotropic_medications): true when the patient has a current Medication with a catalog key, since every vendored-catalog entry is a BH medication by construction — a current free-text medication can't be classified and deliberately doesn't count (an assumption, documented in the ActivePatientRow dataclass, not confirmed CTMS behavior).
- **Primary-diagnosis-driven outcomes (Phase 7 — the 2026-08 decision that governs the three aggregate reports below):** a patient counts toward exactly one condition's response/remission rates — the measure mapped to their episode's primary diagnosis, compared against that measure's own first score in the episode (a per-measure baseline, not necessarily the episode's index baseline). Anxiety-primary patients are tracked on GAD-7, depression-primary on PHQ-9; a dual-diagnosis patient's secondary outcome is deliberately NOT in the headline rates (that's what "primary" means), though their per-measure scores stay visible on Active Patients and the dashboard graphs both. Legacy episodes with no diagnosis fall back to their baseline measure's implied condition. Patients whose resolved measure has no confirmed thresholds (SMFQ, SCARED, PCL-5 in Caseload Statistics, Vanderbilt) are excluded from Caseload Statistics' rates rather than inflating denominators with always-False outcomes; Quality Metrics and Completed Episode Statistics keep their per-measure buckets (0/denominator for unscored measures, per the existing discipline). This is our documented interpretation of the AIMS guide's measure-worded program metrics. Applies to Caseload Statistics (now depression_response/depression_remission/anxiety_response/anxiety_remission, replacing the old phq9_*/gad7_improvement fields), CoCM Quality Metrics, and Completed Episode Statistics. DRR is untouched — HEDIS is index-episode-based by design.
- Clinical Dashboard (Phase 4 — built): GET /reports/clinical-dashboard/{patient_id}, 404 on an unknown patient. Combines enrollment info, demographics, flags, current status, current providers (via CareTeamAssignmentRepository.list_current_by_patient), current clinics, full episode history, and every symptom score sorted by date. The CTMS's "Customize Dashboard View" toggle for which sections show is a frontend concern (which sections to render), not something this endpoint needs to know about — it always returns everything. Phase 5 added a medications section (current first, then past with stop reasons); Phase 6 added profile_entries (every ProfileEntry, grouped by section/sub-field, newest first per sub-field — the frontend derives "current value + history" from that ordering); Phase 7 added measure_trends — the top-of-page graphs, one per treated diagnosis (primary first, then secondary; legacy episodes get one via the baseline fallback) on the reference episode (open, or most recent), each carrying the score series plus server-computed is_response/is_remission so thresholds stay in scoring.py and the frontend only draws.
- Caseload Statistics (Phase 4 — built, columns completed Phase 10): GET /reports/caseload-statistics?group_by=provider|clinic&as_of=. Confirmed CTMS column list (docs/ctms-reference/README.md): Current Caseload, Pts w/ B/C, Avg # B/C, Contacts w/ Scale, # in R/P, # Flagged, # w/ P/C, Not Imprv w/o P/C, Average PHQ First/Last, and the outcome rates. Per Matt (2026-08-07), outcome rates are reported **combined first, then depression and anxiety** — combined_* pools the two per-condition buckets, which is safe because the primary-diagnosis rule makes them disjoint. Every percentage in the row uses caseload_size as its denominator (one documented convention, since the CTMS screenshot's own denominators aren't legible). "Not Imprv w/o P/C" uses the AIMS guide's two-month window (NOT_IMPROVING_REVIEW_WINDOW_DAYS = 60), anchored on as_of. The CTMS frames its two outcome columns negatively (No Response / No Remission); we report them positively — same information, frontend's choice. "Current caseload," per the CTMS's own framing, means what's happening right now off each patient's currently open episode, not lifetime history — a patient with no open episode contributes to caseload_size but nothing else. A provider whose only assigned patient has since been deactivated still appears with caseload_size=0 rather than dropping out of the report, since a Care Team Assignment doesn't automatically end just because Treatment Status changes — those are separate, unlinked events. A per-Psychiatric-Consultant or per-PCP view is this same endpoint filtered client-side by group_label's role suffix, not a separate mode.
- CoCM Quality Metrics (Phase 4 — built): GET /reports/quality-metrics?as_of=, twelve rows oldest-to-newest, the rolling 12-month window ending with as_of's calendar month (today if omitted). Five of the nine documented rates are real: Engagement (≥1 completed Contact that month, per CoCM literature Matt supplied — Hahn et al. 2025; Kim et al. 2026 and Carroll et al. 2026, Psychiatric Services; Blackmore et al. 2022, Psychiatric Services), Depression Response and Anxiety Improvement (the monthly rolling version of the same PHQ-9/GAD-7 response logic used everywhere else, distinct from the DRR Report's windowed version), Measures Completion and Psychiatric Case Review rate (both a direct, explicitly-flagged-as-assumption extension of concepts the registry already tracks — a completed scale on a Contact, a recorded Consultation — scoped to "at least one during the month," with no external citation on file the way Engagement has one). Caseload Reach is always null: it needs an eligible-population denominator this registry has no entity for, and Matt's own research confirms AIMS's exact methodology for it isn't published either, so there's nothing safe to substitute. PTSD/Pediatric Anxiety/Pediatric Depression/Pediatric ADHD Improvement always compute as 0/denominator, per the still-unconfirmed PCL-5/SCARED/SMFQ/Vanderbilt thresholds (see Symptom Score above) — see app/services/quality_metrics.py's module docstring for the full reasoning on every metric.
- Completed Episode Statistics (Phase 4 — built): GET /reports/completed-episode-statistics?year=. Cohort is every episode with end_date in the given calendar year (EpisodeRepository.list_completed_in_year, a plain date-range comparison rather than EXTRACT(year, ...) for portability). Reports total completed episodes, average weeks in treatment, average non-attempt contacts per episode, Relapse Prevention Plan count, a deactivation-reason breakdown seeded with every EndReason value plus a "not_recorded" bucket for episodes closed without one (a real data-quality signal, not something to drop silently), and Depression Response / Anxiety Improvement / PTSD Improvement outcome counts comparing each episode's baseline against its latest same-measure score.
- DRR Report (Phase 4 — built): GET /reports/drr?year=&as_of=. Built from the HEDIS spec Matt supplied directly: Depression Response is a ≥50% PHQ-9 reduction from baseline, Depression Remission is a PHQ-9 score under 5, and the follow-up assessment falls **4-8 months** after baseline (corrected from 4-6 on 2026-08-07 — the CTMS's own Follow-Up PHQ-9 tooltip says 4-8 and Matt confirmed it's authoritative). Three further differences between that tooltip and this implementation are recorded as open questions in docs/ctms-reference/README.md and deliberately NOT resolved: the CTMS's cohort is "first PHQ-9 ≥10 in the year regardless of episode" rather than our index-episode baseline, it applies an age ≥12 criterion we don't, and it includes an episode once 4 months have elapsed rather than once the window fully closes. Each would move real denominators — get Matt's call before changing any of them. The eligible cohort is index episodes (baseline_measure_type=PHQ9) whose baseline_date falls in `year`, but only once that episode's 4-6 month window has fully closed as of `as_of` — an episode with too-recent a baseline is excluded from the cohort entirely rather than counted as a failure, since its outcome is still genuinely unknown. All three rates (Follow-Up PHQ-9 completion, Remission, Response) share one denominator, the full eligible cohort — matching real HEDIS DRR's convention that a missed follow-up counts against the rate rather than being excluded from it, which is what makes "Follow-Up PHQ-9" worth tracking as its own number. Grouped by each patient's current clinic assignment (their primary one if they have more than one); a patient with none groups under "unassigned." See app/services/drr.py's module docstring for the full reasoning — every structural call beyond the HEDIS numbers themselves is flagged there as an assumption, not confirmed methodology.
- Monthly Time Tracker (Phase 4 — built): GET /reports/time-tracker?as_of=. Minutes of service per patient, current month plus trailing 12 (13 months total, per the literal "current month plus trailing 12 months" description), summing duration_minutes across completed (non-contact_attempt) Contacts. A patient appears if they have at least one such Contact anywhere in the window, whether or not they're still on caseload — a program still needs billing minutes for someone deactivated partway through the window. Org-configurable per settings.monthly_time_tracker_enabled (app/core/config.py — a global settings flag, not a per-org database row, per the Multi-tenancy decision above) — the route returns 404 rather than an empty list when it's turned off, so "disabled" isn't confused with "no data."

## Hosted Prototype (Phase 14 — built)

A public, always-current demo so people can click through the platform.
Lives in `deploy/` plus `Dockerfile`, `render.yaml` and `.dockerignore` —
**additive by design**, per the instruction that deployment be done
separately from what was already built. Nothing under `app/` changed at all.
There is exactly **one** frontend exception, deliberately taken and gated:
`pages/Login.tsx` renders a one-click role picker and swaps the PHI notice
for a demonstration-data one when `import.meta.env.VITE_DEMO_MODE === '1'`,
which only the Dockerfile's frontend stage sets. Any other build is
unchanged. It exists because a tester who can't get past the sign-in screen
gets nothing from a demo, and because the standing PHI notice is actively
false on invented data. Keep that the only exception. See
`deploy/README.md` for the full picture, including how to deploy and the
published demo credentials.

Shape: one container, one process, no database service. `deploy/demo_app.py`
mounts the existing FastAPI app at `/api` and serves the built SPA from
`frontend/dist` with an index.html fallback (client-side routes must survive
a hard refresh). Mounting at `/api` is what makes this cost zero frontend
changes — the client already calls `/api/*`, since that's what the Vite dev
proxy rewrites — and makes it same-origin, so there's no CORS config.

**Self-recentring demo data** is the point of the thing. `scripts/seed_demo.py`
already dates everything relative to the day it runs, which is exactly the
"always X days from today" property wanted — but that only holds on the day
it ran. So `deploy/demo_data.py` records the seed date in a one-row
`demo_state` table and re-seeds whenever it isn't today: at boot in
`entrypoint.sh`, and on SPA page load (deliberately on the page load, never
on API requests, so a refresh can't happen underneath in-flight session
traffic; ~2s). `DEMO_REANCHOR_ON_LOAD=0` freezes it. `POST /api/demo/reset`
forces it, and is authenticated like every other router — a public reset
button wasn't a good enough reason to make the unauthenticated-route list
three entries long.

Decisions worth not re-litigating:
- **`demo_state` is not an Alembic migration.** It's deployment bookkeeping,
  not registry schema; the Alembic chain is for the two databases the
  registry actually targets. It also lives outside `Base.metadata` so the
  wipe can't delete the row recording the wipe.
- **On SQLite the schema comes from the models, not the migration chain.**
  `alembic upgrade head` *cannot* run on SQLite — migration `a3613a105946`
  issues `ALTER COLUMN ... DROP DEFAULT`, which SQLite has no syntax for.
  `ensure_schema` is dialect-aware: `create_all` on SQLite, real migrations
  anywhere else. Sound here because a demo database has no history to
  migrate. **Stated tradeoff: the hosted demo exercises the models but not
  the migration chain** — Postgres remains where that gets verified.
- **The SQLite file is ephemeral** (Render's free tier has no disk), which
  for a demo is a feature: a restart returns the scenario to its known
  starting state, and the entrypoint seeds an empty database automatically.
- **One `requirements.txt`**, not a trimmed deploy copy — a second
  dependency list drifts quietly, which is worse than a fatter demo image.

## Authentication (Phase 3 — built)

Every route requires a valid Provider token except POST /auth/login and GET /health — see app/core/deps.py's get_current_provider, applied via `dependencies=[Depends(get_current_provider)]` at the APIRouter level in each routes/*.py file, not repeated per route function. Add that same dependency to any new router; a router built without it is an accidental hole in an otherwise fully authenticated API.

Login is email + password against Provider.hashed_password (PBKDF2-HMAC-SHA256, stdlib `hashlib`, no bcrypt/passlib dependency), returning a JWT (PyJWT, HS256) that the client sends back as `Authorization: Bearer <token>`. POST /auth/login accepts BOTH JSON {email, password} (the frontend/scripts contract) and form-encoded username/password — the latter because get_current_provider's OAuth2PasswordBearer scheme advertises an OAuth2 password flow at that URL, and the interactive docs console's Authorize dialog (like any standards-compliant OAuth2 client) posts form-encoded; found broken during 2026-08-07 UI testing. The form body is parsed with stdlib urllib.parse rather than request.form() to avoid a python-multipart dependency (same stdlib-over-dependency call as hashlib-instead-of-passlib). settings.secret_key signs it — a credential exactly like database_url, read from the environment locally and AWS Secrets Manager in production; the literal default in app/core/config.py is a dev-only placeholder and must never reach a real deployment as-is.

Because POST /providers is itself protected, the very first account can't be created through the API — there's nobody logged in yet to create it. scripts/create_admin_provider.py solves this by talking to the repository layer directly, bypassing the API. Run it once per environment, then create every other Provider through the API as that account.

Not yet built: password reset/change, account lockout after repeated failures, and refresh tokens (the JWT just expires after access_token_expire_minutes and the user logs in again) — reasonable next steps once there's a frontend to build a "forgot password" flow against, not urgent before then.

## PHI and Compliance Constraints

- Never write PHI to browser localStorage or sessionStorage on the frontend. Hold patient data in React state during a session and refetch as needed.
- Every connection to Postgres or Snowflake uses encrypted transport. **Not yet enforced** — there is no sslmode handling in app/core/config.py or app/database.py. Still open.
- Every write to patient status, a flag, or a score gets an audit log entry recording who made the change, what changed, and when. **Built in Phase 13** — see the Audit Log entry under Data Model.
- No credentials in code. Read connection strings from environment variables locally and from AWS Secrets Manager in production.

## What Not To Do

- Don't build reporting endpoints before the core data model and CRUD layer are tested and solid.
- Don't introduce a second ORM or query builder alongside SQLAlchemy.
- Don't add authentication until the data layer works end to end against Postgres.
- Don't hardcode the remission, response, or reminder-cadence thresholds in more than one place.
- Don't invent clinical thresholds for PCL-5, SCARED, SMFQ, or Vanderbilt remission/response. Leave them unscored until AIMS confirms the real numbers. (GAD-7 remission < 5 is NOT in this list — Matt confirmed it 2026-08-07.)
- Don't add response/remission reporting paths that bypass the primary-diagnosis rule (see Primary-diagnosis-driven outcomes under Reporting Requirements) — a patient counts toward one condition's rates, resolved via _episode_condition/_primary_measure_assessment in app/services/reporting.py and the same logic in quality_metrics.py, never toward every measure they happen to have scores for. And don't turn CONDITION_MEASURES into per-report copies; it lives in scoring.py only.
- Don't write an Alembic data migration that matches enum values in lowercase: **SQLAlchemy's Enum stores a PEP-435 enum's NAME, not its value**, so these columns hold `VIDEO` / `FOLLOW_UP` / `CONFIRMED_WITH_PATIENT`, not `video` / `follow_up`. Phase 11's location rename was written against the lowercase values first and silently rewrote nothing — it was caught only by inspecting the pressure database. Any future value-rename migration must match the uppercase name and be verified by actually reading rows back both directions, not just by the migration running without error.
- Don't leave the RPP-contact and episode-close status cascades as something the frontend has to remember to trigger separately. They're server-side side effects in ContactService (record_contact) and EpisodeService (update_episode) precisely so the frontend can't call one and forget the other. The same rule applies to the discuss-with-consultant flag cascade (ContactService) and the Consultation flag-clear/re-set cascade (ConsultationService) — never make the frontend responsible for keeping Patient.needs_psychiatric_review in sync.
- Don't write to patient status, a flag, or a score without an audit entry, and don't add a write route without binding `actor: Provider = Depends(get_current_provider)` and passing it into the service — the audit trail's "who" depends on it, and tests/test_audit_log.py asserts no HTTP route produces an anonymous entry. Same spirit as the router-level auth rule: a short, deliberate list of exceptions (scripts only), not one that grows by accident.
- Don't add update or delete routes for AuditLog, and don't let anything but AuditService write to it. An audit log that can be edited is not an audit log.
- Don't add a standalone "create a Symptom Score" endpoint. A score only ever exists as part of a Contact now (ContactCreate.scores, written through ContactService.record_contact) — one save action for the visit date, every scale score, and the psychiatric-consultant checkbox together, matching the CTMS's own contact-recording form.
- Don't invent the ReminderStatus vocabulary (pending, completed, dismissed) as confirmed either — same "flag it, don't invent it as fact" treatment as ContactLocation. The walkthrough never showed the Reminders page's own status/dismiss controls in enough detail.
- Don't build a new router without adding `dependencies=[Depends(get_current_provider)]` at the APIRouter level (see Authentication above) — the only two exceptions in this codebase are POST /auth/login and GET /health, and that should stay a short, deliberate list, not grow by accident.
- Don't add an org_id/tenant_id column, or an Organization entity, without first rereading the Multi-tenancy entry under Data Model — a future Organization means one NeuroFlow customer org, not a repurposed Clinic Assignment, and that decision should stay made in one place rather than redecided ad hoc when multi-tenancy actually gets built.
- Don't move Monthly Time Tracker's on/off flag onto a database row before an Organization entity actually exists for it to belong to — settings.monthly_time_tracker_enabled (app/core/config.py) is deliberately a plain global flag until then, per the Multi-tenancy decision above.
- Don't label Monthly Time Tracker's minutes "billable" in the UI — the CTMS's own deck is explicit that without EHR integration it lists every recorded minute and "does not distinguish what is billable or not, so providers have to take a look themselves."
- Don't accept the five Relapse Prevention Plan fields on a non-RPP contact type; ContactService rejects them on purpose, so plan content can't exist where no screen would ever show it.
- Don't treat CoCM Quality Metrics' Measures Completion or Psychiatric Case Review rate definitions as confirmed AIMS/NCQA methodology — they're this codebase's own reasonable extension of concepts the registry already tracks, explicitly flagged as such in app/services/quality_metrics.py's module docstring, unlike Engagement which has an actual literature citation behind it.
- Don't edit app/vendor/medication_registry.py — it's a byte-identical copy from bh-cds (see app/vendor/__init__.py) so re-syncing stays a plain `cp`. cocm-registry-specific catalog logic belongs in app/services/medication_catalog.py.
- Don't invent a frequency or stop_reason vocabulary for Medication — both are free text on purpose, same "flag it, don't invent it as confirmed" treatment as ContactLocation and ReminderStatus.
- Don't add update or delete routes for ProfileEntry — it's append-only by design (corrections are superseding entries), which is also what provides its PHI audit trail. And don't promote SECTION_SUB_FIELD_SUGGESTIONS into an enum or into write-validation; sub_field is deliberately free-form with org-configurable suggestions.
- Don't let the profile's Current Medications section accumulate free-text medication ProfileEntry rows — medications are Medication entity rows; that section's only ProfileEntry sub-field is allergies_intolerances. Same rule in spirit for Outcome Measures and Care Team: they render from SymptomScore and CareTeamAssignment, never from free-text profile twins.
- Don't derive a second "is this patient at risk" signal from Safety & Risk ProfileEntry rows — Patient.safety_risk stays the single alerting flag; entries document, the flag alerts.
- Don't let the hosting layer leak into the registry. `deploy/` wraps `app/` and `frontend/dist`; nothing in `app/` may import from or be modified for it. The single sanctioned frontend exception is `Login.tsx`'s `VITE_DEMO_MODE` block (see Hosted Prototype) — anything else demo-specific belongs in `deploy/`, and a second gated flag scattered through the UI is the thing to avoid.
- Don't move `demo_state` into the Alembic chain, and don't "fix" the migrations so they run on SQLite. The chain targets Postgres and Snowflake; SQLite exists here only to make a free, database-less demo possible, and `ensure_schema` already branches on dialect.
- Don't change DRR Report's shared-denominator convention (a missed follow-up counts against every rate, not just the completion one) without rereading app/services/drr.py's module docstring first — it's a deliberate choice modeled on how real HEDIS DRR measures work, not an oversight.
